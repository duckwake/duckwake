# Testing

## Results

Run on a MacBook (Apple Silicon, 10 cores) against DuckDB v2.0.0 and DuckLake 1.1, with a PostgreSQL 16
catalog, Redpanda and MinIO, all from `docker-compose.yml`.

| Gate in the design | Test | Result |
| --- | --- | --- |
| Commit is atomic (Phase 0) | `examples/phase0_*.rs` | One transaction over sink, state, lease and checkpoint tables = one snapshot. A zombie commit is rejected. Time travel to an epoch's snapshot works. |
| `kill -9` at any point, no duplicates or gaps | `scripts/crash_test.sh` | 120k events with late and malformed rows. 12–16 crashes: external `kill -9` and aborts injected at poll, transaction begin, mid-transaction, before and after COMMIT, and maintenance. Sinks match a batch recomputation exactly. |
| Views over views and lake tables (F1) | `scripts/chain_test.sh` | A chain of three views: stateless over Kafka, windowed over its table on `_commit_ts`, windowed again over that table's `window_end`. 40k events, 8 crashes (`kill -9` and aborts at every epoch step); after every crash all three verify, Kafka for the first and time travel for the others, and again after draining (20k lake rows into the second view, 20–40 closed 30 s windows in the third). Passes in order and with all four worker flags (pipelined). Dropping a view another view reads is refused; an update to a lake table that a windowed view reads, after its window closed, is a late correction in the view's late-data table while the view, the chain and the worker run on. |
| Views over tables whose rows change (F2) | `scripts/retract_test.sh` | A generator rewrites `shop.accounts` (400 rows written before the views, about 640 at the end) with inserts, updates, deletes and mixed transactions, some updating rows and then deleting them: 6.8k–7.8k deletes and updates during 8 crashes. Seven views: counted rows with `_commit_ts`, a grouped aggregate with `min`/`max`, `DISTINCT`, counted rows that repeat, an aggregate over those, rows of the grouped aggregate, and a `UNION ALL` of the table and the aggregate (two change feeds). After every crash and after catching up, each view verifies against its batch query at its checkpoint's snapshot. A reset of the grouped aggregate replays it, and its two readers follow through the change feed and verify. Passes in order and with all four worker flags (pipelined). C4: two windowed views over retracting inputs, `acc_windows` over the table (2 s windows on `_commit_ts`, with `min`, `max`, `count(DISTINCT)` and `median`) and `acc_game_windows` over `acc_by_game`, both with late-data tables; they verify after every crash and after the upstream's reset, and the changes to closed windows (400 in a local run) are late corrections. Runs without Docker (`PG_LOCAL=1`). |
| Upsert views (C2) | `scripts/upsert_test.sh` | A topic of 40k order updates over 3,000 keys (`produce --keys`): message keys as JSON objects and plain text, each key in one partition, every 13th message a tombstone, every 17th sent twice, every 7th with a stale version. Three upsert views (last message wins; highest version wins; highest version behind a filter) and two views reading their tables through the change feed (a filter; an aggregate with `min`/`max` and `count(DISTINCT)`). 8 crashes (`kill -9` and aborts at every epoch step); after every crash all five verify, and again after draining. The upsert views are also checked against the topic read with `duckwake sql`, with SQL written in the script rather than the engine's, and the upsert views write no dead letters. The versioned view's state holds exactly its table's rows. Upsert views with an aggregate or without their key column, and a version without a key, are refused. A reset of the versioned view three epochs back replays it and its reader, which verify. Runs in order and with all four worker flags (pipelined). |
| Debezium sources (C3) | `FORMAT=debezium scripts/upsert_test.sh` | The upsert suite over Debezium change events (`produce --keys --debezium`): the first tenth as snapshot reads, then inserts and updates; deletes as a `d` event and a tombstone, every fifth without a message key; every fourth event and key wrapped as with `schemas.enable`; timestamps as epoch microseconds and amounts as strings. The source has no `event_time`. Everything the upsert suite checks, plus: a view without `upsert_key` and a window over the source are refused, and at the end an event carrying `__debezium_unavailable_value` fails all three upsert views with an error that names the event and says to set `REPLICA IDENTITY FULL`. Runs in order and pipelined. |
| Debezium end to end (C3) | `scripts/debezium_e2e_test.sh` | A real PostgreSQL 16 with logical replication and Debezium's PostgreSQL connector 3.6.3 in Kafka Connect (`docker compose --profile debezium`, started by the script), with Connect's defaults (`schemas.enable` on) plus `decimal.handling.mode=string` and three-partition topics. Debezium snapshots 2,000 orders, then streams 40 rounds of inserts, updates, deletes and primary-key changes, some inside transactions. Four views read it: the table's mirror, a filtered upsert view, an aggregate over the mirror's change feed, and a mirror of a table with large text values. The worker is killed 6 times and Connect restarted once (Debezium resends what it had not committed); all views verify after each crash. After draining, each view equals the PostgreSQL table, compared with SQL over the table exported with `\copy`, and no view wrote a dead letter. Then an update that leaves a TOASTed value out (`REPLICA IDENTITY DEFAULT`) stops the docs view with an error that says what to fix, while the orders views keep running. |
| Backfill and retention (F3) | `scripts/backfill_test.sh` | Two tables of 200,000 rows each, written before any view; six views read them with `start := 'earliest'` (a filter, a grouped aggregate with `min`/`max`, `DISTINCT`, an aggregate's readers, 2 s windows and 10 s windows over those) and one with `start := 'latest'`, 5,000 rows per epoch. A generator inserts, updates and deletes rows while the worker is killed 6 times mid-backfill (kill -9 and injected aborts); after every crash each view verifies against its batch query at its checkpoint's snapshot, up to its backfill cursor. At the end the filter holds all 19,845 matching rows and the `latest` view only the 4,503 rows written after it. With expiry every 2 s, a paused view keeps the lake's oldest snapshot at its position (snapshots 360 to 478 kept; commit times recorded for the 232 of the 359 expired that wrote rows) and verifies once started again. A reset to an expired epoch is refused; a reset of the 2 s windows empties the 10 s windows that read them, which backfill again (77 windows before, 98 after) and verify. A reset to epoch 0 after the start snapshot expired recomputes the filter (all 19,999 matching rows) and the `latest` view (still only rows written after it), and rerunning the `latest` view's create with `--if-exists update --start latest` reports `unchanged`. Runs against PostgreSQL alone (`PG_LOCAL=1` for one on localhost:55432, without Docker); about 6 minutes. Passes in order and pipelined. |
| dbt-duckwake | `scripts/dbt_test.sh` | The example project in `dbt/example` (a Kafka source and six views: windowed, filter, grouped, a view over a view, one over a lake table, and one added later) deployed with dbt-duckdb 1.11.1 and DuckDB 2.0.0 while events stream in and a worker runs. The first run creates and starts everything, a second changes nothing, a new `epoch_interval` alters the views in place, a changed query fails until `--full-refresh`, which refuses to leave a reader behind and with `-s big_spend+` drops and recreates it, a view added over a running one fills from its rows, and the source gains a column. Once the topic ends every view catches up and `dbt test` passes (`duckwake_verified` on every view, `unique` and `not_null` on their tables); `duckwake_drop_orphans` lists, then drops, a removed model's view. Steps 1 to 3 also pass against PostgreSQL alone. |
| Automatic failover (P2) | `scripts/failover_test.sh` | Three workers spread five views started without a worker, while 120k events stream in. A catalog stall of 15 s (every commit held up by a lock on DuckLake's snapshot table, reads going on) moves no view. `kill -9` of one: its views move in 11–13 s with a 10 s lease timeout. A frozen worker (SIGSTOP): its views move in 10–14 s, also when it froze inside its catalog transaction (PostgreSQL ends that session after the lease timeout, so the others' commits go on); thawed, its in-flight commit is fenced and it lets go, or it exits. A drained worker: its views move in 2–3 s. A restarted worker takes views again. All five views verify exactly. Passes in order and with all four worker flags (pipelined). |
| Kafka SASL and TLS (P2) | `scripts/kafka_auth_test.sh` | The test views read through the local Redpanda's SCRAM listener in plaintext, its SCRAM listener over TLS (test CA), and its TLS listener that requires a client certificate; 20k events each, drained and verified, with `verify` reading Kafka through the same listener. Refused: a password written into the source (at create time), a wrong password, an unset password variable, and a plaintext client on a SASL listener (each view fails within 10 s with the reason, and the worker runs on). `KAFKA_AUTH=sasl_ssl scripts/crash_test.sh` passes: 12 crashes, every view exact. |
| Object storage (P2) | `LAKE_STORAGE=s3 scripts/crash_test.sh`, `LAKE_STORAGE=s3 scripts/retract_test.sh` | The lake's data files in a bucket of the local MinIO, with credentials from the AWS variables and the catalog password from `PGPASSWORD`. The crash test (12 crashes, maintenance merging and flushing to the bucket) and the F2 gate (change feeds and time travel read back from the bucket) pass, every view exact. |
| Rebalancing (P2) | `scripts/rebalance_test.sh` | Five views (one pinned) on one worker, started before their topics exist (the worker waits, nothing fails), while 240k events stream in. A second and a third worker join: the views spread to them once their cooldown has passed (14–17 s and 3–5 s with a 15 s cooldown), the pinned view stays, no view moves twice within its cooldown, and a balanced cluster makes no moves. A rolling restart of all three workers moves no view. A drained worker hands everything away in 2 s and takes nothing back. The pinned view's worker is killed: the view fails over in 13 s and goes home 3 s after the worker returns. A worker killed in the middle of a drain: its views fail over. All five views verify exactly. Planner unit tests in `failover.rs`. |
| Schema changes (P4) | `scripts/schema_test.sh` | Two workers, five views, events streaming. A column added to the running source: the views keep their columns and commit on; a duplicate column and two bad types are refused. Two running views replaced (one windowed, with its late-data table): both recompute from the start with the new definition within 3 s, the new column filled; the workers and other views go on. Replacing a view another view reads is refused. `alter-view` restarts a running view with its new epoch interval, continuing from its epoch. `stop` then `drop` at once, three times, with the epoch in flight: fenced or dropped mid-epoch, no worker fails. Every view verifies exactly. |
| Limits (P4) | `scripts/limits_test.sh` | One worker, the five test views plus `late_guard` (`max_late_rows` 1) and `state_guard` (`max_state_rows` 50): each fails alone within 8 s, with the limit in the log and `duckwake_views_failed_total` 2; the other views commit on. Raised with `alter-view` and started again, both catch up; all seven verify exactly. Then 1.5M events of ~1 KB through a `DISTINCT` over every event, under a 64 MB DuckDB limit and 32 MB of spill (`--max-spill`): epochs of 1M rows run out of memory, the worker halves them until they fit and verifies exactly. Before the spill cap the step depended on the runner: with room to spill (1 GB on one run) DuckDB fitted every epoch and the limit was never exercised. |
| dbt-duckwake publishing | `scripts/mirror_dbt_test.sh` | `scripts/mirror_dbt.sh` against a local repository standing in for duckwake/dbt-duckwake, with git alone: the layout holds exactly the files git tracks under `dbt/` plus `LICENSE`, and its README has no link left pointing out of `dbt/`; the first publish creates `main` and an unchanged tree pushes nothing, from the same clone or a fresh one; a release tag on the tree `main` holds points at `main`, and one on another tree gets a commit of its own on top of `main`, which does not move; a tag is published once, and the same tag over other content is refused; `dbt/dbt_project.yml` carries the `Cargo.toml` version. |
| Monitoring discovery (P4) | `scripts/monitoring_test.sh` | Prometheus from the compose profile, with no list of workers. Two workers with `--metrics` are discovered from the lake through one worker's `/sd` within 15 s and scraped under their names; a third that starts is scraped within 30 s, with no configuration change; stopped cleanly, it leaves within 30 s and its alert never fires; a worker killed with `-9` stays a target, down, and `DuckWakeWorkerDown` goes pending. |
| Alert rules (P4) | `promtool test rules deploy/prometheus/duckwake-alerts.test.yml` (CI job `monitoring`) | A stuck view fires and an idle one does not; a view falling behind fires and one under the 30 s floor does not; state near its limit; a failed view, firing then clearing; a worker down and then none up; 2% dead letters. A unit test checks that the rules and the dashboard name only series a worker exports. |
| Zombie worker after failover | `scripts/fencing_test.sh` | w1 commits epochs 1–3, then stalls 15 s with its epoch-4 transaction open. The views move to w2, which continues from epoch 4. w1's commit is rejected. The result verifies exactly. |
| 5k events/s, p95 latency < 30 s | `scripts/throughput_test.sh` | 600k events of ~1 KB at 5,000/s, 10 s epochs. Per epoch (~50k rows): ~0.45 s poll+stage, ~0.15 s commit. Lag stays ~0. An event is committed at most one epoch interval plus ~0.6 s after it arrives; windowed results also wait for the window to close plus the watermark delay. |
| Matches batch SQL | `verify` in every script | Multiset equality of each sink with the view run as one batch query over everything committed. Late rows and dead letters are also checked. |

| `duckwake_reset` | `scripts/reset_test.sh` | Rewind to epoch 6, replay, and the sinks end identical (verified). |
| Arrow decode vs SQL decode | `scripts/catchup_test.sh` | One worker drains 600k events of ~1 KB through three views: 34,049 events/s with Arrow against 25,306 with the SQL decode (1.35×), read + stage 0.89 s against 1.63 s per epoch, peak memory 382 MB against 2,392 MB. Both verify exactly. |
| Parallel processing (worker flags) | `scripts/scale_bench.sh`, all suites with `WORKER_FLAGS` | 16 views on one worker drain a backlog at 40.5k events/s with all four flags, against 21.7k without (1.87×). ## Running the tests

CI (`.github/workflows/ci.yml`) runs on every pull request and every push to `main`. One job runs clippy
(warnings fail it) and the unit tests and builds the binaries and the extension once. Every suite below then
runs in its own job against the same `docker-compose.yml` stack on Linux: crash then reset, fencing,
failover, rebalance, Kafka auth, chain, retract, backfill, dbt, retention, decode, catch-up (100k events), shared readers, server, extension and composed, and
crash, failover, rebalance, chain, retract and backfill again with all four worker flags, crash with its sources over
SASL_SSL and its lake on MinIO, and retract on MinIO. A failed job uploads the worker logs. `ci-passed`
is green only when every job is. The throughput test, the scale benchmark and the soak only measure, so
they stay out of CI.

The test scripts reset the lake and the topic themselves:
`scripts/crash_test.sh`, `scripts/fencing_test.sh`, `scripts/throughput_test.sh`, then `scripts/reset_test.sh`.
`scripts/chain_test.sh`, `scripts/retract_test.sh`, `scripts/backfill_test.sh`, `scripts/upsert_test.sh`, `scripts/failover_test.sh`, `scripts/rebalance_test.sh` and
`scripts/kafka_auth_test.sh` are standalone. `KAFKA_AUTH=sasl_plaintext|sasl_ssl|mtls` points the sources of any suite built on the
shared test views at an authenticated listener (producers stay on the open one), and `LAKE_STORAGE=s3` puts
any suite's data files in the local MinIO. Every suite takes the catalog password from `PGPASSWORD`.
`scripts/retention_test.sh`, `scripts/decode_test.sh` and `scripts/catchup_test.sh` are standalone.
`scripts/dbt_test.sh` is too; it needs Python 3 and the extension (`scripts/build_extension.sh`), installs
dbt-duckdb into `.venv-dbt` (or set `DBT` to a `dbt` that has it) and keeps its DuckDB extensions in
`.lake/duckdb_extensions`.
`DECODE=sql|arrow|auto` picks the source's decode for every script that uses the `clicks` source
(default `auto`).
`cargo run --release -p duckwake_core --example phase_a_arrow_decode` is Phase A of the Arrow ingest plan.
It decodes the same messages with today's SQL decode and with `decode.rs` (Arrow, falling back to SQL for
any form it can't match exactly), checks the outcomes are identical on a hostile corpus, and times both
on 50k soak-shaped events.
`scripts/decode_test.sh` is the same differential in the engine: one topic of hostile messages read by a
source that decodes in SQL and one that decodes in Arrow, each feeding the same view; sinks and dead letters
must be equal row for row. `scripts/catchup_test.sh` times a worker draining a backlog in each mode.
`POINTS="before_commit after_commit" scripts/crash_test.sh` limits the crash test to chosen injection points.
`WORKER_FLAGS="--stage-threads 4 --pipeline --shared-readers --lean-commit"` runs any test's workers with
the parallel-processing flags; with `--pipeline` the crash test also aborts while an epoch is staged ahead
of a commit (`staged_ahead`). `scripts/shared_reader_test.sh` creates a view late and rewinds another while
events stream in; both must catch up, join the shared reader and verify.
`scripts/composed_test.sh` uses the DuckDB 2.0 CLI on both ends: a plain DuckDB loads the extension, runs a
worker and serves itself over Quack; a second one attaches with `CONNECT`, creates four views, drops a lookup
table to make the worker fail and restart, recreates it and verifies everything.
`scripts/serve_test.sh` drives a `duckwaked` entirely over Quack: create, start, pause, reset and verify the
three test views, and check `/metrics`. `scripts/extension_test.sh` does the same in one DuckDB session with
the extension loaded and a worker inside it.
`scripts/scale_bench.sh` runs 1, 2, 4, 8 and 16 views (the playground's mix) on one worker at a fixed
rate, or with `CATCHUP=1` through a backlog, and appends epoch period, freshness, stage and commit time
(statements vs `COMMIT`), CPU and memory to `.lake/bench/*.csv`; `FLAGS` and `LABEL` name the variant.

`scripts/soak_test.sh` runs the design's soak test: 24 h at 5,000 events/s of ~1 KB with maintenance
enabled. It uses its own catalog database (`soak`), data path (`.lake/soak`) and topic, so it does not
touch the playground. Every minute it samples lag, freshness, snapshot count, catalog size, inlined
rows, Postgres dead tuples, file counts and worker memory. `scripts/soak_report.sh` summarizes a run by
hour, during or after it; `BUCKET="10 minutes"` makes the buckets finer. To stop early, run
`kill "$(cat .lake/soak/run.pid)"`. `DURATION`, `RATE`, `EPOCH` and the maintenance cadences are
environment variables. Snapshots are kept for 12 h by default, so a 24 h run reaches steady state
halfway through. The topic is capped at 1 GiB per partition, because Docker's VM disk is small.

Once retention has deleted a topic's oldest events, `verify` checks the retained range only. It starts
from the oldest checkpoint whose offsets are all still retained, and compares the output that depends only
on later events. For an append sink, that is the rows of later epochs. For a windowed sink, it is the
windows that start after every event time the job had seen by that checkpoint. The report's `from_epoch`
says which checkpoint was used. A global aggregate depends on every event, so it cannot be verified once
its topic has been trimmed.
